# Generated artifact lifecycle

This policy applies prospectively to generated data added after a supplied Git baseline. Existing historical HNG/HDB/HGE/SFH/SRM artifacts are grandfathered and remain unchanged; they are not retroactively reclassified or deleted by this guard.

## Artifact classes

### A. `GIT_AUTHORITY`

Keep in Git. This class covers canonical data, Gold and reviewed annotation, frozen selections, and human semantic decisions. These files are historical or semantic authority and require their existing review/protection contracts.

### B. `GIT_COMPACT_RESULT`

Keep in Git when reasonably compact. This class covers semantic projections, metrics, compact manifests, and deterministic result summaries. Large new results require an explicit path classification before they become part of the current contract.

### C. `EXTERNAL_ARCHIVE_DEFAULT`

Do not commit by default. This class covers raw provider/API envelopes, HTTP transport payloads, retry responses, and large immutable request/response dumps. A Git exception must be explicit, reviewed, and accompanied by enough manifest metadata to verify an external archive.

### D. `EPHEMERAL_REBUILDABLE`

Do not commit by default. This class covers temporary replay state, debug output, and deterministic scratch/intermediate files. Rebuildable does not mean semantically disposable: protected inputs and review authority remain governed by their own contracts.

## Current policy

The machine-readable policy is [config/generated-artifact-policy.json](../config/generated-artifact-policy.json). Generated roots currently include `data/generated/`, `data/derived/`, `site/src/generated/`, and `site/public/generated/`.

The conservative thresholds are:

- files above 5 MiB receive a warning;
- files above 20 MiB require an explicit policy classification or an approved exception;
- raw provider/API paths and ephemeral/debug paths require approved exception metadata before Git tracking.

The default generated class is `GIT_COMPACT_RESULT`, but that default is intentionally not an explicit classification for the 20 MiB rule. Specific raw/provider and debug/scratch path classes are ontology-free storage policy, not historical or Classical Chinese semantics.

An approved exception must include an ID, path or pattern, artifact class, reason, and review reference. An externally archived payload descriptor is expected to retain:

```text
schema
stage
run_id
archive_sha256
files.path
files.sha256
files.size_bytes
```

## Non-mutating audit and CI guard

Run the audit against the previous main ref or a merge-base:

```bash
python3 scripts/audit_repository_growth.py \
  --baseline HEAD^1 \
  --check-new
```

It reports total tracked bytes, baseline bytes, new and changed generated bytes, large generated files, new raw-provider files, warnings, classifications, and policy violations. It never deletes, rewrites, regenerates, or stages files.

`--check-new` fails only for violations on paths absent from the supplied baseline. Existing large or raw historical paths are listed as `grandfathered_existing_generated_files` and cannot fail the new-growth check. Positive size changes to existing paths are reported separately, so a builder mutation remains visible without turning the historical repository into a file-by-file exception list.

The Pages workflow fetches sufficient history and runs this guard against the prior main commit before its normal rebuild steps. `npm run audit:growth` exposes the same audit locally; `npm run test:c3` runs the focused policy tests.

## Exception example

An explicitly reviewed raw response could be allowed through a policy overlay such as:

```json
{
  "id": "reviewed-transport-fixture-001",
  "path_or_pattern": "data/generated/example/raw-api/response.json",
  "artifact_class": "EXTERNAL_ARCHIVE_DEFAULT",
  "reason": "required immutable fixture for a reviewed transport contract",
  "review_reference": "review-record-001"
}
```

This is an exception to the storage default, not semantic authority and not permission to write canonical facts.

## Contract boundary

The lifecycle guard is deliberately separate from historical validators. It does not update protected hashes, accept SC1/WP1 regeneration, alter canonical Persons/Relations/Gold, or migrate existing experiment payloads. Future cleanup may evaluate cold archival or content-addressed descriptors only after the archive can be restored and verified from its manifest.
